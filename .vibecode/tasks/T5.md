# T5 — SSE polling → push (B6)

## Goal
Spec implicitly requires no polling: the session-level SSE stream
`/api/v1/sdlc/stream/:workflowId` polled `getPipelineResponse` every 2s,
wasting a DB roundtrip per connected client even when nothing changed.

## Approach
Per user instruction "Tái dụng gateBridge, không viết lại":
1. Add `subscribeProject(projectId, cb)` to gateBridge — fans out every
   `emit(taskId, event, data)` to a project-level listener (uses a
   reverse `taskToProject` map populated in `requestGate`).
2. Replace the polling loop in `streamPipelineStatus` with:
   - One initial snapshot fetch (so the client has current state on connect).
   - `gateBridge.subscribeProject` for push.
   - A SLOW fallback (10s, was 2s) that ONLY catches terminal states
     (`qa_complete`, `failed`) — these aren't otherwise broadcast.

## Files changed
- `backend/src/services/gateBridge.js`:
  - New `projectSubscribers` Map + `taskToProject` reverse index.
  - `emit()` now also fans out to project-level subscribers.
  - New `subscribeProject(projectId, listener)` exported helper.
  - `requestGate` registers `taskId → projectId` for fan-out.
- `backend/src/controllers/SdlcController.js`: `streamPipelineStatus`
  rewritten end-to-end (snapshot → push → 10s terminal-fallback).
- `backend/tests/integration/gateBridge.subscribeProject.test.js`: new
  unit test (3 cases — basic unsubscribe, no leak after unsubscribe, no
  cross-project leak).

## Decisions captured
- 10s fallback for terminal states, not full removal of the poll — keeps
  the contract honest if `qa_complete`/`failed` are ever produced without
  an explicit emit. Cost is negligible (1 DB hit / 10s per stream).
- `taskToProject` is in-memory and not pruned — matches existing
  `subscribers` Map lifetime (the `_clearAll` test helper wipes both).
