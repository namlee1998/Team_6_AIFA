# 04 — Ownership Drift (Phase 2)

> **Status:** READ-ONLY. For every important object, identify the
> single canonical owner (per Phase-0 baseline), the current owner(s)
> (per source), the drift, the evidence. Mark each as PASS / WARNING /
> FAIL.
>
> "Important objects" are: `approvalId`, `decisionId`, `featureRequest`,
> `observability`, `claude_result`, `task status`, `gate`, `review`,
> `approval`. The list is taken from the Phase-2 prompt.

The single-owner rule was stated in the freeze: "One artifact. One
owner. Never create shared ownership."

## 1. `approvalId`

### Single owner (canonical)

A pending gate has exactly one `approvalId`, generated by
`gateBridge.requestGate` (`backend/src/services/gateBridge.js:51-83`).
The DB row is the durable truth; the in-memory `pending` map is the
live truth during a Claude SDK call.

### Current owner(s)

- `gateBridge.requestGate` — **single writer** (UUID generated
  via `uuidv4()`).
- `gateBridge.resolveGate` — **single mutator** (resolves the row).
- `PendingGate` model — **single durable owner** of the row.

### Drift

None.

### Evidence

- `backend/src/services/gateBridge.js:52` (`approvalId = uuidv4()`).
- `backend/src/services/gateBridge.js:88-89` (single persist).
- `backend/src/services/gateBridge.js:165` (single resolve).

### Mark

**PASS.**

## 2. `decisionId`

### Single owner (canonical)

`decisionId` is the idempotency key for structured HITL decisions
(`submitStructuredDecision`, `releaseManager.submitReleaseDecision`).
The DB column `HitlDecision.decisionId` is `@unique`
(`schema.prisma:208`).

### Current owner(s)

- Producer: every `HitlDecision.create` call site
  (`SdlcWorkflowService.js:204, 325, 432, 442, 521, 2134`,
  `releaseManager.js:80`).
- Consumer: `HitlDecision.findByDecisionId(decisionId)` in
  `SdlcWorkflowService.js:278` and `releaseManager.js:46` (for
  idempotency check).

### Drift

None at the producer side. `decisionId` is generated by
`uuidv4()` at every producer call. The release manager enforces
the key (line 27).

#### Warning (not a drift)

The legacy `submitGateDecision` path (SdlcWorkflowService.js:185-231)
writes `HitlDecision.create(...)` WITHOUT a `decisionId`. The legacy
path therefore has no idempotency. It is reachable
(`POST /sdlc/tasks/:task_id/gate-decision`, routes/sdlc.js:35) and is
covered by an integration test (`sdlc.handoff.test.js`).

**Evidence**:
- `backend/src/services/SdlcWorkflowService.js:204-213` (legacy
  create, no `decisionId`).
- `backend/src/services/SdlcWorkflowService.js:325-336` (structured
  create with `decisionId`).

### Mark

**WARNING** (legacy path bypasses idempotency).

## 3. `featureRequest`

### Single owner (canonical)

`featureRequest` is the original user input to the SDLC pipeline. The
single canonical owner per the freeze baseline is `Task.observability.featureRequest`,
seeded by `workflowOrchestrator.runArchitectureAgent:107`.

### Current owner(s)

- **Owner A**: `Task.observability.featureRequest` (orchestrator:107,
  `runPOAgent:358`).
- **Owner B**: `AgentArtifact.contentText` / `contentJson` of type
  `'feature_request'` written by `_saveAgentData`
  (SdlcWorkflowService.js:1829, 1940-1944). Re-written by every
  agent whose output includes a `feature_request` key (mock only).
- **Owner C**: The HTTP body of `POST /run-architecture-agent` (passed
  through to `SdlcWorkflowService.runArchitectureAgent:featureRequest`).

### Drift

Two durable sources of truth for the same input string: the
`Task.observability` blob and the `AgentArtifact` row. A rewriter
that edits one without the other creates a desync.

The `compactContext` whitelist in `claudeCodeRunner.js:91-127`
controls which context keys reach the AIFA Context. For
`po-agent`, `featureRequest` is in the whitelist. The downstream
agent sees the in-process `featureRequest` argument, not the
persisted `Task.observability.featureRequest`. So at runtime the
two owners are read by different consumers.

### Evidence

- `backend/src/services/workflowOrchestrator.js:104-108` (owner A
  writer).
- `backend/src/services/SdlcWorkflowService.js:1829, 1940-1944`
  (owner B writer).
- `backend/src/agents/claudeCodeRunner.js:93-101` (PO context
  whitelist).
- `03_PIPELINE_GAPS.md G-15` (Phase-1 audit).

### Mark

**FAIL.** Two durable owners for the same object.

## 4. `observability`

### Single owner (canonical)

`Task.observability` (schema.prisma:106) is meant to be a single
JSON blob whose schema is owned by the workflow runtime.

### Current owner(s)

- `workflowOrchestrator.runArchitectureAgent:107`
  (`{ featureRequest }`).
- `workflowOrchestrator.runPOAgent:358`
  (`{ repo, featureRequest }`).
- `SdlcWorkflowService._saveAgentData:2011-2015`
  (merged with `completedData.observability`).
- `agentDispatcher.markTaskFailed:514-528` (adds `failure` block).
- `middleware/requestContext.js:17-20`
  (`setContext({ taskId, phase })` for logging).

Five writers. The merged-write at `_saveAgentData` uses the spread
operator (`{...liveTaskForObservability?.observability ?? {},
...completedData.observability ?? {}}`); last-write-wins on
conflicting keys.

### Drift

Multiple writers, no schema. The middleware path (requestContext)
operates on a separate per-request scope, so the conflict is
logically scoped: the request context never lands in
`Task.observability`. But the four `Task.observability` writers do
race when the SDK is mid-flight.

### Evidence

- `backend/src/services/workflowOrchestrator.js:104-108, 356-361`
- `backend/src/services/SdlcWorkflowService.js:2011-2015`
- `backend/src/services/agentDispatcher.js:514-528`
- `backend/src/middleware/requestContext.js:1-39`

### Mark

**WARNING.** Multiple writers; one of them (the request context) is
correctly scoped; the others race on the JSON blob.

## 5. `claude_result`

### Single owner (canonical)

`claude_result` is a per-run snapshot of the Claude SDK's outcome
(`claudeCodeRunner.normalizeOutput`, claudeCodeRunner.js:307-313,
written under `output.observability.claude_result`). The single owner
is the claude-code runner.

### Current owner(s)

- Writer: `claudeCodeRunner.normalizeOutput` (claudeCodeRunner.js:307-313).
- Persisted via: `_saveAgentData:2011-2015` → `Task.observability`.
- Reader: **none found**.

### Drift

Producer writes; no consumer reads. Orphan write.

The mock runner does NOT write `claude_result`. So the field is
present only on claude-code runs.

### Evidence

- `backend/src/agents/claudeCodeRunner.js:307-313` (writer).
- `backend/src/services/agentDispatcher.js` (mock path; no
  `claude_result` field).
- `grep -rn 'claude_result' backend/src` — only the writer and
  `agentDispatcher`'s mock short-circuit comment
  (`mock: true`, claudeCodeRunner.js:537).

### Mark

**FAIL.** Orphan write; no reader.

## 6. `task status`

### Single owner (canonical)

`Task.executionStatus` is the canonical state machine
(`taskLifecycleService.TRANSITIONS`, taskLifecycleService.js:11-21).
Single owner of transitions: `taskLifecycle.transition` and its
race-tolerant variant `transitionIfPresent`.

### Current owner(s)

- `taskLifecycle.transition` / `transitionIfPresent` — canonical
  owners of `executionStatus`.
- Eight direct `Task.update({ status: … })` writers mutate the
  LEGACY `Task.status` field (not `executionStatus`), bypassing
  the state machine. See `03_PIPELINE_GAPS.md G-3`,
  `05_STATE_DRIFT.md DR-012`.

### Drift

Two parallel state fields on the same row:
- `Task.executionStatus` (state machine; canonical).
- `Task.status` (free-form string; legacy).

The two can disagree. Consumers that branch on `Task.status` see a
value that is not bound to `TRANSITIONS`. The literal
`'PENDING_TOOL_APPROVAL'` (legacy langchain path) is not in any
documented state set.

### Evidence

- `backend/prisma/schema.prisma:67, 84` (both columns declared).
- `backend/src/services/taskLifecycleService.js:11-21`.
- 8 direct writers listed in `03_PIPELINE_GAPS.md G-3`.

### Mark

**FAIL.** Two state fields on one row, only one governed by a
state machine.

## 7. `gate`

### Single owner (canonical)

A pending gate has one durable truth: the `PendingGate` row. The
in-memory `gateBridge.pending` map (gateBridge.js:28) is a
convenience lookup, not a separate source of truth.

### Current owner(s)

- `gateBridge.requestGate` — **writes both** the in-memory map and
  the DB row (gateBridge.js:69-89).
- `gateBridge.resolveGate` — **mutates both** (gateBridge.js:154-194).
- `PendingGate` model — durable owner.
- `gateBridge.pending` Map — in-memory owner.

### Drift

Dual truth. After a backend restart, the in-memory map is gone and
only the DB row remains. `hasPending(approvalId)`
(gateBridge.js:196) reads the in-memory map only; recovery path
uses `findPersisted(approvalId)` (gateBridge.js:239-246) for the
DB row.

The two owners are written together on `requestGate` and
`resolveGate` (in the same critical section). So under normal
operation they stay in sync. Under restart or `awaiting_gate` race
they diverge.

For `kind='release'` specifically: the in-memory entry is created
but never awaited (no SDK is paused). It is dropped when
`resolveGate` is called from `releaseManager.submitReleaseDecision`.
The DB row is also resolved. So `kind='release'` creates two
durable records: a `PendingGate` row AND a `HitlDecision` row.

### Evidence

- `backend/src/services/gateBridge.js:28, 51-83, 154-194, 196, 239-246`
- `backend/src/services/releaseManager.js:106-194`

### Mark

**WARNING.** Dual writers under normal operation; recovery path
required for divergence. The `kind='release'` path is structurally
redundant.

## 8. `review`

### Single owner (canonical)

A `review` is a `HitlDecision` row, owned by the structured HITL API
(`submitStructuredDecision`,
`SdlcWorkflowService.js:264-336`).

### Current owner(s)

- `submitStructuredDecision` (canonical, with `decisionId`).
- `submitGateDecision` (legacy, no `decisionId`).
- `resolveOutputReviewGate` (per-agent output-review approve/reject).
- `_handleGateRejection` (reject → re-run; possibly
  `escalation_required`).
- `_autoApproveSafeOutput` (auto-approve).
- `resolveApproval` question branch (`decision='CLARIFICATION'`,
  `action='answer'`).
- `releaseManager.submitReleaseDecision` (FINAL_RELEASE).

### Drift

The legacy `submitGateDecision` path
(`SdlcWorkflowService.js:185-231`) writes a review WITHOUT the
canonical `decisionId` idempotency key. Replays cannot be
deduplicated.

The `decision` enum has at least one novel value (`CLARIFICATION`)
that does not appear in the documented
`{APPROVE, REJECT, REQUEST_CHANGES}` set (see freeze doc `06_EVENT_INVENTORY.md`
and `08_CURRENT_KNOWN_ISSUES.md I-17`).

### Evidence

- `backend/src/services/SdlcWorkflowService.js:185-231` (legacy
  path, no `decisionId`).
- `backend/src/services/SdlcWorkflowService.js:264-336` (canonical
  structured HITL path).
- `backend/src/services/SdlcWorkflowService.js:381-396`
  (`decision='CLARIFICATION'`).

### Mark

**WARNING.** Legacy path bypasses idempotency; novel `decision`
value not in documented enum.

## 9. `approval`

### Single owner (canonical)

An `approval` is the approve-side `HitlDecision` row, produced by
the structured HITL `submitStructuredDecision` (action=`approve` or
`edit_approve`) or by `resolveOutputReviewGate` (action=`approve`)
or by `_autoApproveSafeOutput` (action=`auto_approve`).

### Current owner(s)

As in §8. All seven callers above can produce an `approval`.

### Drift

Same as `review`: legacy path lacks idempotency. The
`action='auto_approve'` path is a different code path
(`_autoApproveSafeOutput`) but is owned by the same module
(`SdlcWorkflowService`).

The release `approval` is owned by `releaseManager.submitReleaseDecision`
only.

### Evidence

- `backend/src/services/SdlcWorkflowService.js:2123-2162` (auto-approve).
- `backend/src/services/SdlcWorkflowService.js:466-591`
  (output-review approve).
- `backend/src/services/SdlcWorkflowService.js:325-336` (structured
  approve/edit_approve).
- `backend/src/services/releaseManager.js:76-92` (release approve).

### Mark

**PASS for canonical path. WARNING for legacy path (no
`decisionId`).**
